# D-520 — Release-db sans approbation humaine, migrations comprises : la porte d'écriture du schéma devient le merge d'une PR contre-revue par Codex et `wn-reviewer` ; un merge à la fois, sentinelle liée au run, constat par conteneur, aucune plage horaire (amende D-087)

- Date : 2026-11-14
- Statut : accepté. Le responsable a demandé le 2026-11-14 que « les
  release db doivent pouvoir s'approuver sans moi ». Il a ensuite répondu à
  deux questions de la liste commune, chaque fois contre l'option
  recommandée : `20261114-1035-integrateur` (portée : « Toutes, migrations
  comprises ») et `20261114-1340-d` (heure : « Aucune plage »). Entre-temps,
  il a donné à l'intégrateur une délégation permanente pour approuver les
  runs (§6). Texte rédigé par l'assistant, lot du carnet
  `release-db-sans-approbation-1`.
- Domaine : workflow `release-db` et son environnement GitHub ;
  `.claude/rules/pr-revue-et-release-db.md` §3 à §5 ;
  `.claude/rules/db-prisma.md` ; `docs/claude/REGLES_PR_MERGE.md` ;
  `docs/DEPLOIEMENT_RELEASE_DB.md` ; `CLAUDE.md`, règle « Base de
  production ».
- **Amende** [[D-087]] sur un point : l'approbation humaine du run cesse
  d'être l'unique porte d'écriture du schéma. Le mécanisme de [[D-087]] ne
  change pas : one-off dans l'image de production, empreinte des migrations
  re-vérifiée dans le conteneur, drapeau constaté, sentinelle liée au run,
  aucune URL de base chez GitHub.
- **[[D-086]] §1-2** reste supplanté. Le « go explicite du responsable
  avant merge » de son §1 n'est pas rétabli : le regard humain qui demeure
  est celui du §5. Son §3 (vérification par conteneur) ne change pas.
- **Remplace** l'arbitrage du 2026-11-13 : approbation conservée au
  responsable pour les migrations à risque, et migration additive pure
  sans lui seulement après un classifieur (lot `orchestration-6`). Ce
  classifieur n'est plus à construire.
- **Ne touche pas** : les phases de [[D-374]] et la sonde
  `scripts/wn-sonde-release-db.mjs`, relues pour ce lot (§3) ; la
  séparation entre migration et code consommateur ; [[D-044]] §3 (le chemin
  clinique déclenche la release) ; la garde de fraîcheur du déployeur
  ([[D-248]]) ; le staging.

**§1 — La porte.** Aucun run `release-db` n'attend plus de clic humain.
C'est vrai pour une migration comme pour un push clinique ([[D-044]]),
une table signée hors de `clinical/` ([[D-389]] §5, [[D-416]],
[[D-480]] §5) ou un contrat de préflight. L'environnement `release-db`
garde trois choses :

- sa restriction de branche : seul `main` atteint le jeton Scalingo ;
- son minuteur de 5 minutes, qui devient un temps d'arrêt. Sans relecteur,
  il n'y a plus de demande de déploiement à rejeter : le seul arrêt est
  l'annulation du run (`gh run cancel <id>`) avant le lancement du one-off.
  Au-delà, annuler le job n'arrête pas le one-off : seul
  `scalingo one-off-stop` l'arrête (piège 3). C'est la file qui a mergé,
  et qui suit le run (§3), qui surveille ces cinq minutes ;
- le secret `SCALINGO_API_TOKEN`.

Il perd sa liste de relecteurs requis (§6). Ce qui ouvre l'écriture est
le merge sur `main` d'une PR qui a passé le §2.

**§2 — Avant le merge d'une PR qui porte une migration.** Ces points
remplacent l'approbation. Chacun se constate au moment du merge, aucun ne
se suppose :

1. **Contre-revue Codex P0** ([[D-505]] §4) sur le diff poussé, déposée
   sur la PR. Chaque constat y a son verdict. Si Codex est indisponible
   ([[D-505]] §7), la migration ne se merge pas : la passe se fait par le
   bloc du skill, porté par le responsable, ou la PR attend.
2. **`wn-reviewer` donne son GO sur le sha de tête**, comme le veut
   l'exception migration de `REGLES_PR_MERGE.md`. Un commit poussé après
   le GO demande une revue de l'écart.
3. **CI vert sur la tête** (`wn-attendre-ci` → `0`), avec la parité
   schéma ↔ migrations de T3. Puis le contrôle sur l'arbre fusionné et la
   sonde release-db à `0` (`wn-merge` 7 bis et 7 ter).
4. **Migration seule** (`pr-revue-et-release-db.md` §3) : le code
   consommateur n'est pas dans la PR, ou reste derrière un drapeau éteint.

Une release sans migration nouvelle (chemin clinique, table signée,
contrat) n'a pas de condition de plus : les gardes de sa classe restent
celles qu'elle a aujourd'hui (signature, décision clinique, barème de
revue). Son run rejoue les contrats contre la production, et un préflight
rouge empêche l'écriture. Mais son `migrate deploy` applique **toute**
migration restée en attente sur `main`. Le §3 bis l'encadre.

**§3 — Un merge à la fois.** La file qui merge une migration la suit
jusqu'au constat. Elle lit la sentinelle `WN_RELEASE_DB_OK id=<run>` du
run, puis vérifie que la première ligne des déploiements Scalingo est la
tête de `main` (piège 6). Enfin, elle lit `_prisma_migrations` par
conteneur, agrégée par nom. Une seconde migration ne se merge pas avant
ce constat : il n'y a jamais qu'une migration en vol. Pour les autres
merges, la sonde décide, et ses phases ne changent pas. Une fois les
relecteurs retirés (§6), la phase 1 de [[D-374]] ne dure plus que le
minuteur ; d'ici là, elle dure jusqu'à l'approbation de l'intégrateur.
Pendant la phase 1, les PR qui ne touchent aucun chemin gelé mergent, et
le déployeur retient leur code jusqu'à l'application ([[D-374]] §1). La
phase 2 commence quand le run est constaté hors de `waiting`, quelle
qu'en soit la cause : aucun merge jusqu'à sa conclusion. La sonde lit
l'état `waiting` de la même façon, qu'il vienne d'un relecteur ou du
minuteur. Elle reste donc inchangée. Entre la conclusion du run et le
constat par conteneur, la sonde rend `0` pour une seconde migration :
« une migration à la fois » tient ici à la discipline de la file, et
aucune garde ne la vérifie encore (§8).

**§3 bis — Une migration non appliquée gèle les chemins déclencheurs.**
Un run annulé, ou rouge avant écriture, laisse sur `main` une migration en
attente. Le prochain push sur un chemin déclencheur (migration, clinique,
table signée, contrat) lance un run dont le `migrate deploy` l'appliquerait
sans nouvelle revue. Tant que cette migration n'est pas appliquée et
constatée, aucune PR qui touche un chemin déclencheur ne se merge. La
sortie est l'une de ces deux voies :

- le revert de la migration, par une PR classée P0 ;
- sa reprise sous le §2, par un `workflow_dispatch` humain (§5).

La sonde ne le voit pas encore : un run conclu, même annulé, ne gèle rien.
La garde qui manque (« migration non appliquée ⇒ gel des chemins
déclencheurs ») est au §8.

**§4 — L'heure : aucune plage.** Une migration qui ajoute une colonne à
une table servie la casse jusqu'à la fin du one-off. La fenêtre de panne
dure le run seul, sans attente d'approbation : de 14 à 20 minutes de bout
en bout sur les runs récents, minuteur compris. Cette panne est acceptée
à toute heure (`20261114-1340-d`). L'étape « choisir le créneau » est
retirée. Reste l'interdit de merger une migration « pour y revenir plus
tard » : le merge ouvre le run, et la file le suit jusqu'au §3.

**§5 — Ce qui reste humain.** La présente décision ne lève aucun de ces
gestes :

- la demande explicite d'écrire une migration et la confirmation distincte
  avant de l'écrire (`CLAUDE.md`, le crochet « demande ») ;
- la confirmation du SQL destructif ;
- toute suppression ou correction de données ;
- la sortie d'un run rouge après déploiement, correctif en avant ou retour
  de slug (piège 5) ;
- la sortie d'un run coincé ([[D-374]] §5), qui devient son annulation ;
- le déclenchement manuel (`workflow_dispatch`), et la relance d'un
  ancien run (« Re-run jobs », `gh run rerun`) : sans relecteur, l'un et
  l'autre écrivent sans autre clic.

**§6 — Entrée en vigueur.** Le texte s'applique au merge de cette
décision. La configuration suit en un geste distinct : retirer la règle
`required_reviewers` de l'environnement `release-db`. Ce geste se fait
**après le merge du lot de gardes du §8**. Il revient au responsable, ou
à l'intégrateur sur son accord daté, écrit au registre des messages. Il se
constate par
`gh api repos/{owner}/{repo}/environments/release-db --jq '.protection_rules'`,
qui doit rendre le minuteur et la politique de branche, sans relecteur.
Jusqu'à ce constat, la délégation du 2026-11-14 tient la porte :
l'intégrateur approuve lui-même par l'API, sous les conditions du §2 et du
§3. Après le constat, elle n'a plus d'objet.

**§7 — Contreparties assumées.**

- **Le jeton Scalingo n'attend plus de clic.** Tout job qui déclare
  `environment: release-db` sur `main` l'atteint après le minuteur. Ce
  n'est pas neuf : l'environnement `deploy-production` porte lui aussi un
  secret `SCALINGO_API_TOKEN`, sous sa seule politique de branche, sans
  relecteur ni minuteur (API lue le 2026-11-14). Le confinement repose sur
  la politique de branche et sur la revue des PR. Un déclencheur qui
  s'exécute dans le contexte de `main` satisfait cette politique, par
  exemple `issue_comment` sur un dépôt public. Sont donc classées P0, comme
  le dit désormais `POLITIQUE_REVUE.md`, les PR qui :
  - modifient `release-db.yml`, `deploiement-production.yml` ou ce que
    leurs runs exécutent en production ;
  - ajoutent `environment: release-db` ou `environment: deploy-production`
    à un autre job.

  Les `CHEMINS_GELES` de la sonde ne couvrent pas tout ce que le one-off
  exécute : `web/package.json` et `web/package-lock.json` fixent le CLI
  Prisma de l'image. Ce trou existait déjà, et il est nommé ici. Le banc
  `scripts/release-db-invariants.test.mjs` garde les invariants de
  `resume` : aucun secret hors du `GITHUB_TOKEN` du run, son exception
  nommée, et aucune permission d'écriture. Le jeton Scalingo n'y est donc
  pas atteignable.
- **L'identité n'est pas distinguée.** Les sessions écrivent sous le
  compte du responsable. L'approbation était le seul acte qui lui restait
  propre, et elle l'était déjà moins depuis la délégation. Le journal des
  déploiements de l'environnement reste la trace de ce qui est parti.
- **Le second regard sur le contenu du push disparaît.** Le résumé du job
  `resume` reste écrit, mais plus personne ne le lit avant l'écriture. Pour
  une PR de migration, ce qu'il disait (« regarder le push à la main »)
  passe au §2, avant le merge. Ses deux avertissements, le diff en échec
  et la borne inconnue, surviennent aussi sur des pushes sans migration
  nouvelle. Ils n'arrêtent rien : `resume` réussit, et la release part
  après le minuteur (§8).

**§8 — Le lot de gardes, avant le geste du §6.** Un lot de code
(`release-db-sans-approbation-2`, file D, P0) remplace par des gardes ce
qu'un lecteur humain rattrapait. Il porte quatre gardes :

1. **Sonde.** Une migration de `main` non appliquée, après un run conclu,
   gèle les chemins déclencheurs (§3 bis), et une seconde migration avant
   le constat de la première (§3).
2. **`resume`.** Il échoue sur un diff en échec, et la borne inconnue est
   tranchée.
3. **Environnements.** Un banc parcourt `.github/workflows/*.yml` et
   refuse `environment: release-db` et `environment: deploy-production`
   hors des jobs admis.
4. **Chemins gelés.** `web/package.json` et `web/package-lock.json`
   rejoignent les `CHEMINS_GELES`.

Le lot corrige aussi les messages des crochets qui parlent encore d'une
release « approuvée » (`protect-wellneuro-files.mjs`,
`guard-supabase-mcp.mjs`). Au premier run après le §6, la file constate
que le minuteur seul met le run en `waiting` et que la sonde y lit la
phase 1. Jusqu'au geste du §6, la délégation tient la porte, et
l'intégrateur lit le résumé avant d'approuver.

**Ce qu'elle ne décide pas** : la forme d'une approbation automatique par
un tiers (bot, application GitHub) ; le retrait du minuteur ; le
`workflow_dispatch` sans humain ; les migrations sur une autre base que
la production Scalingo.

**Faits** (questions `20261114-1035-integrateur` et `20261114-1340-d`,
API lue le 2026-11-14) :

- l'environnement `release-db` porte trois règles : `required_reviewers`
  (le compte du responsable seul, `prevent_self_review` désactivé),
  `wait_timer` de 5 minutes et `branch_policy` ;
- quatre release-db en 24 heures (#2065, #2092, #2080, #2096) ont chacune
  tenu les merges jusqu'à leur approbation, dont une nuit entière pour
  #2092 ;
- sur les trente derniers runs, une release approuvée dans la foulée dure
  de 14 à 20 minutes de bout en bout. Celles qui ont attendu une
  approbation de nuit ont duré de 6 à 8 heures.
