# D-467 — La garde anti-recul de `release-db.yml` est retirée : l'auto-déploiement Scalingo étant coupé et le workflow ne déployant que la tête de `main`, elle ne protège plus de rien et fait lire « à relancer » une release appliquée (option C1 ; liée à D-248)

- Date : 2026-11-09
- Statut : accepté. Arbitrage du responsable du 2026-11-09, option C1, citée mot pour mot : « C1 : la retirer ». Texte rédigé par l'assistant sur cet arbitrage.
- Domaine : pipeline `release-db` (`.github/workflows/release-db.yml`, dernière étape du job `release`) ; ses bancs (`scripts/release-db-comportement.test.mjs`, `scripts/release-db-invariants.test.mjs`, parité du déployeur dans `scripts/wn-deploiement-deployer.test.mjs`) ; `docs/DEPLOIEMENT_RELEASE_DB.md`, `docs/RUNBOOK.md`, `.claude/rules/pr-revue-et-release-db.md`.
- Amende : la garde anti-recul de `release-db` posée le 2026-09-23, que [[D-248]] annonçait comme « sans objet au lot 4 », et [[D-374]] §2 (phase 3) pour la seule mention de la fin rouge volontaire. Ne modifie pas [[D-087]] : l'écriture en base reste une migration relue, puis une release-db approuvée par un humain.
- **Ne touche pas** : les gardes d'avant-écriture (drapeau `WN_MIGRATIONS_PAR_RELEASE_DB`, calme avant déclenchement, refus si la tête apporte une migration ou un changement clinique non jugé, « commit attendu = dernier déployé », empreinte des migrations, sentinelles liées au run, contre-épreuve `migrate status`) ; le déployeur `deploiement-production.yml` / `scripts/wn-deploiement-deployer.mjs` et sa propre garde finale ; la lecture d'un run rouge après application par `classerRunReleaseDb` (elle sert encore aux runs antérieurs) ; le gel par phases de [[D-374]] ; aucune migration, rien sous `web/src/lib/clinical/`.

**§1 — Le fait.** Le 2026-09-23, le run `release-db` d'un vieux commit (`de290fd7`) a déployé la tête puis conclu au vert ; Scalingo, qui auto-déploie un commit dont tous les checks ont conclu, a redéployé le vieux commit une minute après (run 35563094380, quatre lots retirés pendant six heures). Une étape finale, la « Garde anti-recul », a alors fait finir en échec volontaire tout run dont `main` avait avancé : la release n'était pas annulée, seule la conclusion du run passait au rouge, seul signal que Scalingo lisait.

**§2 — Ce qui a changé depuis.** [[D-248]] a coupé l'auto-déploiement (`integration-link-update --no-auto-deploy`, bascule du lot 3, constatée le 2026-09-25 ; relevée le 2026-11-09 : `scalingo --app wellneuro --region osc-fr1 integration-link` → « Automatic deployment: ✘ »). Les déploiements passent par `.github/workflows/deploiement-production.yml` et `scripts/wn-deploiement-deployer.mjs`, qui ne déploient que la tête. Plus aucun vert de `release-db` ne peut donc réveiller le déploiement d'un vieux commit.

**§3 — Le coût de la garde.** Elle fait finir en rouge une release qui a bien eu lieu. Le cas du 2026-11-09 : la release-db de #1930 (run 42528009082) appliquée, sentinelle et contre-épreuve vertes, mais run rouge parce que `main` avait avancé. Un rouge qui veut dire « appliquée, ne pas relancer » apprend à ne plus lire les rouges de ce workflow, et un lecteur pressé relance une release déjà faite.

**§4 — Décision.** L'étape « Garde anti-recul — le commit du run a été dépassé » est supprimée de `release-db.yml` ; un run dont la tête a dépassé le commit approuvé, sans migration ni changement clinique nouveau, conclut au vert comme tout run qui a appliqué sa release. Rien d'autre ne change dans le workflow. Les quatre bancs de la garde sont retirés ; un banc d'invariant la remplace (§5).

**§5 — Ce qui protège encore de l'anti-recul.**
- Le workflow ne déploie que la tête de `main` : son seul déclenchement est `integration-link-manual-deploy main`, qui déploie une branche, jamais un SHA, une archive ou un slug antérieur. Un banc d'invariant verrouille cette propriété : tout autre déploiement dans le workflow, ou le retour de la garde, fait rougir `scripts/release-db-invariants.test.mjs`.
- L'étape de déclenchement ne s'abstient que si le déploiement le plus récent est le commit approuvé et en succès (correctif du 2026-09-23, run 35854104186) ; sinon elle redéploie la tête.
- Le déployeur de [[D-248]] ne déploie que la tête, avec son observation de recul (`scripts/wn-deploiement-observation.mjs`, étape « Observation » du CI) qui rougit un recul constaté.
- La règle du constat après chaque release (`.claude/rules/pr-revue-et-release-db.md`, piège 6) : la première ligne de `scalingo --app wellneuro deployments` est la tête de `main`.

**§6 — Condition de validité.** Cette décision tient tant que l'auto-déploiement Scalingo reste coupé et que `release-db.yml` ne déploie que la tête. Si l'auto-déploiement est rétabli (retour arrière de la bascule, `docs/RUNBOOK.md` § « Revenir à l'auto-déploiement »), la garde se rétablit dans le même revert, avant le geste qui le réactive : le RUNBOOK le dit. De même, un chemin qui déploierait un commit antérieur à la tête dans `release-db.yml` rouvre la question avant tout merge.

**§7 — Historique intouché.** Les fragments `changelog.d/`, handoffs, entrées du journal et du `SESSION_LOG` qui décrivent la garde restent tels quels : ils disent ce qui était vrai à leur date.
