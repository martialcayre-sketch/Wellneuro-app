**§1 — Ce qu'est l'orchestrateur.** C'est une routine claude.ai qui se
réveille à cadence fixe. Elle est créée depuis l'interface des routines,
dépôt sélectionné. Une routine créée par l'outil de session n'a ni dépôt
ni outils (constat ci-dessus) ; sa création est donc un geste du
responsable. Sa consigne, hors dépôt, tient l'adresse de la page de suivi
de la file D, qui n'entre jamais dans le dépôt.

À chaque réveil, elle joue une **passe** :

1. lire l'interrupteur d'arrêt (§8) ;
2. lire le carnet, le registre des messages et l'état GitHub ;
3. calculer ce qui est dû par les règles de [[D-510]], le superviseur
   en lecture seule l'y aidant ;
4. pour chaque lancement dû, et dans la limite du plafond (§5) :
   - relire l'interrupteur ;
   - créer la ligne d'intention (§3) ;
   - lancer ;
5. écrire une ligne de journal (§9) ;
6. s'arrêter.

Elle ne tient aucun lot. Son seul état, ce sont ses lignes d'intention et
son journal, dans la base ; le reste se relit dans les registres et sur
GitHub. Ce n'est pas un service. Les sessions qu'elle lance sont des
sessions cloud (« files en cloud ») ; l'intégrateur, les E2E et les lots
qui les exigent restent au Mac.

**§2 — Périmètre.**
- **La routine peut** :
  - lire les registres, GitHub et le dépôt ;
  - créer ses lignes d'intention et de journal ;
  - lancer une session cloud neuve sur un lot désigné (§3, §4) ;
  - écrire des lignes `autre` de [[D-503]], et seulement celles-ci :
    - à la boîte D : le constat d'hygiène (§6), une ligne par cause
      d'arrêt d'elle-même et par jour (§8), une file sans lot lançable
      depuis vingt-quatre heures (§9) ;
    - à la boîte de la file : les lots de la voie Mac et les lots
      orphelins (§3).
- **La routine ne fait jamais** :
  - merger, fermer ou renvoyer une PR ;
  - déclencher, approuver ou annuler un run `release-db` ;
  - signer, ou répondre à une question, de quelque nature qu'elle soit,
    y compris par l'accord de [[D-505]] §6, qui reste celui d'une
    session qui agit ;
  - prendre, ranger, débloquer, reprendre ou passer à `fait` une ligne du
    carnet, ni en inscrire une ;
  - écrire dans les collections `questions` et `reponses`, ni supprimer
    une ligne ;
  - pousser une branche, toucher un worktree du Mac, supprimer une
    branche, un worktree ou un fichier ;
  - archiver ou relancer une session ;
  - lire ou écrire la production.
- **Une session lancée** a les droits d'une session de file, sauf ceux-ci,
  qu'elle n'a jamais :
  - merger, sous le filet de vingt minutes de [[D-454]] comme ailleurs.
    Le filet d'un lot lancé revient à sa file, sur la voie Mac (en-tête) ;
  - prendre un second lot (§4) ;
  - lancer `test:e2e` ou `test:worktree`.
- **Aucune ligne `orchestrateur`** ne vaut autorisation, accord daté ni
  réponse, au sens de [[D-520]] §6 ou de la liste commune.

**§3 — Succession dès « prête » (exigence 1).** Pour chaque file en
service (§10), la passe cherche le lot suivant selon [[D-510]] §2 : la
ligne `pret` au plus petit ordre, dont l'`apres` est `fait`.

Si ce lot relève de la voie Mac, elle le signale (ci-dessous) et passe au
lot `pret` suivant de la même file, dans l'ordre. Les dépendances entre
lots s'écrivent dans `apres` ([[D-510]] §3), que la passe respecte
toujours : l'ordre seul ne les porte pas.

- **Conditions du lancement.** Elle ne lance une session sur ce lot que si
  six conditions sont toutes réunies :
  1. le lot est lançable en cloud (ci-dessous) ;
  2. aucun lot de cette file n'est `pris` sans PR déclarée ;
  3. aucune session lancée de cette file n'est vivante (§5) ;
  4. le plafond du §5 et le budget du §7 le permettent ;
  5. l'interrupteur du §8 est ouvert ;
  6. la ligne d'intention a pu être créée.

  Une déclaration « prête @<sha> » libère la file : la passe suivante lance
  le lot d'après. Le merge reste à l'intégrateur.
- **Ligne d'intention.** Avant chaque lancement, la passe crée sans
  version, dans la collection `orchestrateur_lancements`, un document
  d'identifiant `<lot>--v<version de la ligne lue>`. Si ce document
  existe déjà, la création est refusée et rien n'est lancé : deux passes
  qui se chevauchent ne lancent pas deux fois. La ligne porte la file,
  l'heure et, une fois connu, l'identifiant de la session.
- **Lot lançable en cloud.** Il faut trois choses à la fois :
  - `lieu` vaut exactement `cloud` ;
  - `nature` vaut exactement `ordinaire` ;
  - l'identifiant, la file, la branche et le handoff passent les contrôles
    du §4.

  Tout le reste va à la voie Mac : `lieu` absent ou inconnu, `nature`
  absente, autre ou inconnue, champ malformé. Dans le doute, le Mac.

  Va aussi à la voie Mac un lot dont une ligne d'intention existe déjà à
  la version lue : il a été tenté sans prise (§5). La passe ne réécrit pas
  sa ligne du carnet. Elle le tient pour un lot de la voie Mac tant que sa
  version ne change pas.

  Les deux champs se posent à l'inscription et s'écrivent dans
  `ROLES_MACHINES.md` au lot de mise en service. Ne sont jamais `cloud`,
  quelle que soit leur nature :
  - un lot de migration, de `schema.prisma`, de logique clinique,
    d'authentification ou de configuration de revue ;
  - un lot qui exige T2 ou T3 ;
  - un lot qui numérote une décision, tant que la réservation est refusée
    en cloud ;
  - un lot qui touche un crochet, un réglage ou l'outillage de release
    ([[D-374]]) ;
  - un lot dont un écran se relit en navigateur ;
  - un lot qui lit la production par conteneur ;
  - un lot de risque P0, qui exige Codex ([[D-505]] §7), tant que Codex
    n'est pas constaté dans une session lancée ;
  - un lot qui demande un dépôt privé.

  La session lancée revérifie au départ que son lot n'en relève pas. S'il
  en relève, elle fait trois choses, puis s'arrête :
  - elle passe `lieu` à `mac` ;
  - elle remet le lot à `pret` ;
  - elle écrit une ligne `autre` à la boîte de la file.

  Le lot reste ainsi prenable au Mac, sans motif de blocage hors de
  [[D-510]] §3.
- **Voie Mac.** Pour un lot `pret` de la voie Mac, la passe ne lance rien :
  elle n'ouvre pas de session sur le Mac. Elle écrit une seule ligne
  `autre` à la boîte de la file (« lot … pour le Mac »), une fois par lot
  et par version de la ligne. Une session ouverte au Mac le prend comme
  aujourd'hui.
- **Lot orphelin.** Un lot qu'une session lancée a laissé `pris` sans PR
  ne se relance pas. C'est le cas :
  - d'une session morte ;
  - d'un renvoi qui a vidé `pr` ([[D-510]] §7) ;
  - d'un lot sans nouvelles, dont `tenu_le` a plus de quatre heures
    ([[D-510]] §8).

  La passe le signale une fois à la boîte de la file, comme lot de la voie
  Mac. Sa reprise suit [[D-510]] §8, par une session ouverte au Mac. En
  attendant, la file reste occupée (condition 2) : le signal est la seule
  sortie.

**§4 — Session neuve et premier message (exigence 2).** Chaque lot est une
session neuve : c'est le `/clear` entre deux lots, fait par
construction.

Une session lancée tient **un seul lot**, et s'arrête dans quatre cas :
- si son lot relève de la voie Mac (§3) : elle passe `lieu` à `mac`,
  remet le lot à `pret` et écrit une ligne `autre` à la boîte de la
  file ;
- après sa déclaration « prête », son handoff et sa ligne `prete` au
  registre ;
- après avoir rangé son lot `bloque` avec son motif et écrit son handoff ;
- si la prise conditionnelle échoue (lot déjà pris), ou si l'échéance de
  son intention est passée (§5) : elle écrit alors une ligne `autre` à la
  boîte D, sans prendre ce lot ni un autre.

C'est l'amendement de [[D-510]] §4, §6 et §7 (en-tête) ; la passe d'après
lance le lot suivant.

- **Contenu du premier message.** Il suit un gabarit fixe, versé au dépôt
  par le lot de mise en service (§10). Il ne contient que :
  - l'identifiant du lot et sa file ;
  - l'identifiant de la ligne d'intention et son échéance (§5) ;
  - la branche :
    - une branche neuve depuis `origin/main` ;
    - ou, si la ligne porte une branche poussée, une branche neuve tirée
      de celle-ci ([[D-510]] §8) ;
  - le handoff à lire : celui que désigne la ligne, s'il y en a un ; sinon
    celui qu'indique la règle de [[D-372]] §2 ;
  - l'adresse de la page de suivi, tirée de la consigne de la routine,
    hors dépôt ;
  - la boîte à lire et à accuser ([[D-503]]) ;
  - les interdits permanents de `CLAUDE.md` et du handoff, par renvoi ;
  - la primauté de ce message sur l'enchaînement de [[D-510]] ;
  - l'ordre de s'arrêter dans les quatre cas ci-dessus, sans prendre
    d'autre lot.
- **Contrôles avant lancement.** Sans eux, rien n'est lancé et le lot va à
  la voie Mac :
  - l'identifiant de lot répond à `^[a-z0-9-]+$` ;
  - la file est l'une de `A`, `A bis`, `B`, `C`, `D` ;
  - la branche, si la ligne en porte une, répond à
    `^[a-z0-9][a-z0-9._/-]*$` et passe `git check-ref-format --branch` ;
  - le handoff, si la ligne en porte un, est un chemin
    `docs/claude/handoffs/AAAA-MM-JJ-HHMM-<slug>.md` présent sur
    `origin/main` ou sur la branche nommée.

  Un lot neuf, sans branche ni handoff, passe ces contrôles.
- **Aucun texte libre.** Le message ne recopie aucun texte libre du
  registre : ni titre, ni motif, ni question, ni message. La session lit la
  ligne elle-même, comme une donnée ([[D-510]] §9). Le lot est désigné au
  sens de `CLAUDE.md` (« lot désigné »), sans la priorité qu'une
  désignation du responsable reçoit de [[D-510]] §2 : la passe suit
  l'ordre du carnet. La session prend le lot par écriture conditionnée
  ([[D-510]] §4).

**§5 — Plafond et collisions (exigence 3).**
- **Session vivante.** C'est une ligne d'intention qui remplit quatre
  conditions :
  - elle n'a pas expiré ;
  - son lot n'a pas reçu de `pr` ;
  - son lot n'est ni `fait`, ni revenu à `bloque` ou à `pret`, ni
    orphelin (§3) ;
  - une fois le lot pris, son `pris_par` désigne toujours la session
    lancée.
- **Échéance.** Une ligne d'intention expire si son lot n'est pas `pris`
  par la session lancée dans les trente minutes : c'est un **lancement
  sans prise**. Le lot est alors tenu pour un lot de la voie Mac (§3),
  sans que sa ligne soit réécrite, et le lancement entre dans le compte du
  §8. Passé cette échéance, que le premier message lui donne, la
  session lancée ne prend plus son lot (§4).
- **Plafond global.** La ligne d'intention, propre à un lot, ne protège
  pas `N` contre deux passes qui se chevauchent sur deux files. Le pilote,
  à une file, n'est pas exposé. La généralisation demandera un bail
  global, à décrire dans son lot.
- **Plafond cloud.** Au plus une session vivante par file, et au plus `N`
  en tout. Pendant le pilote (§10), `N` = 1, file D seule. La valeur de la
  généralisation se fixe sur le rapport du pilote, par une question de la
  liste commune.
- **Mac.** L'orchestrateur n'ajoute aucune charge au Mac : il n'y lance
  rien. Il ne signale pas un lot de la voie Mac tant qu'un autre lot de la
  même file est `pris` sans PR déclarée.
- **CI.** Chaque session a sa branche. Le groupe de concurrence de
  `ci.yml` est propre à la référence, et chaque job a sa base éphémère :
  deux lots ne partagent aucun état de CI.
- **PR.** Deux lots de files différentes peuvent toucher un même fichier.
  Le chevauchement se voit à « prête » et à l'étape 7 bis de l'intégrateur,
  qui merge un à un. Une branche en conflit va à l'arbitrage du
  responsable ([[D-518]] §2), jamais à une fusion d'office.
- **Tests.**
  - « Un seul E2E » vise `test:e2e`, sur la base partagée : au Mac seul,
    un run à la fois, comme aujourd'hui.
  - `test:worktree`, qui joue aussi Playwright, reste au Mac. Ses ports
    sont dérivés du chemin du worktree (PostgreSQL 5500-5599, application
    3100-3199), d'où des runs parallèles sans contamination (règle 2 de
    `ROLES_MACHINES.md`).
  - Une session lancée ne joue ni l'un ni l'autre : ses lots sont ceux qui
    n'exigent que T1 (§3). Les jouer en cloud relèverait d'une décision à
    part.
- **Migration et release-db.** Une migration à la fois et une release-db à
  la fois, comme aujourd'hui ([[D-520]] §3, [[D-374]]). Aucune session
  lancée ne porte de migration (§3). Le gel de [[D-374]] s'applique au
  merge, donc à l'intégrateur.

**§6 — Hygiène du dépôt (exigence 4).** À la cadence retenue (§7), une
passe joue en constat seul, dans son clone :
- `node scripts/wn-etat-reel.mjs`. Dans un clone frais, `.wn/state.json`
  est absent : ses confrontations sont vides, et le script affiche
  « 0 écart(s) ». La passe le rend « non confronté », jamais « zéro
  écart » ;
- `bash scripts/nettoyage-branches.sh`, **sans** `--appliquer`, si et
  seulement si `gh` est authentifié ;
- `bash scripts/repo-hygiene.sh audit-only` : inventaire et doublons,
  sortie dans `.repo-hygiene/`, ignoré par Git, jamais poussé.

Elle rend une ligne `autre` à la boîte D : les comptes, les écarts, les
branches que le constat dit prouvées, et les doublons, par identifiants
(branche, PR, chemin). Aucun texte de fichier n'y est recopié.

Un clone frais ne voit ni les branches locales ni les worktrees du Mac :
son constat porte sur les branches distantes et les PR, et se reconfirme
au Mac avant toute suppression. Le constat du Mac et toute suppression
restent à la copie principale, par délégation du responsable :
`--appliquer`, `apply-safe`, branches et worktrees. Jamais depuis la
routine.

**§7 — Budget.** Le budget se compte en passes et en lancements, parce que
la routine ne lit pas de dépense :
- une cadence de passes ;
- un plafond de lots lancés par jour, à l'heure de Paris ;
- une cadence d'hygiène.

Les valeurs de départ sont celles de la réponse à `20261118-2312-d`. Tant
qu'elle n'est pas répondue, la routine ne s'allume pas.

**Modèle de la passe** : Sonnet, effort medium, choix de cette décision.
La passe applique des règles écrites ; elle ne tranche rien. Le choix se
revoit sur le rapport du pilote. Les sessions lancées suivent le défaut de
`CLAUDE.md`.

**Plafond quotidien atteint** : la passe ne lance plus rien jusqu'au
lendemain, et le journalise.

**Session lancée trop longue** : aucune borne de dépense ne l'arrête. Sa
durée est bornée par son lot. Quand `tenu_le` a plus de quatre heures,
sans PR, son lot devient orphelin (§3) et il est signalé ; le responsable peut l'archiver
dans l'interface.

Chaque ligne de journal porte la durée de la passe et, quand l'interface
la donne, sa dépense. Le rapport du pilote les additionne. Une révision du
budget passe par une question.

**§8 — Arrêt d'urgence.** Deux interrupteurs, et l'un suffit.
- **La routine elle-même**, désactivée dans l'interface des routines par
  le responsable : plus aucune passe.
- **Le document d'arrêt** `orchestrateur/arret`, dans la base de la page
  de suivi de la file D.
  - **Lecture.** La passe le lit en premier, puis le relit avant chaque
    lancement. Elle ne lance que si son champ `arret` vaut exactement le
    booléen `false`. Toute autre valeur l'arrête : document absent ou
    illisible, champ absent, `null`, `"false"`, texte. Tout s'arrête alors,
    hygiène et lignes `autre` comprises, sauf la ligne de journal :
    l'interrupteur fermé se lit au cockpit, sans signal de plus.
  - **Écriture.** Une session pose `arret: true` d'elle-même, sur un
    signal sérieux, ou sur la parole du responsable. Seule la parole du
    responsable, dans la session qui agit, fait poser `false`. Le cockpit
    n'écrit pas ailleurs que dans `reponses` (§10).

**Arrêts d'eux-mêmes**, interrupteur ouvert. La passe ne lance rien et le
journalise dans trois cas :
- sa lecture est partielle ou dégradée : un doute rend l'action
  indéterminée, jamais verte ;
- la journée de Paris compte déjà trois lancements sans prise (§5) ;
- deux sessions lancées visent le même lot.

Chaque cause donne une seule ligne `autre` à la boîte D par jour, et non
une ligne par passe.

**Sessions déjà lancées.** Un arrêt ne les interrompt pas : chacune finit
son lot, ou le responsable l'archive dans l'interface.

**§9 — Journal.** Une ligne par passe, dans la collection
`orchestrateur_journal` de la même base, créée sans version et jamais
supprimée.

**Identifiant** : `AAAAMMJJ-HHMM-orch`, à l'heure de Paris. L'horloge du
système est lue puis convertie vers `Europe/Paris`, car le conteneur tourne
en UTC. Si l'identifiant est pris, il est suffixé `-2`, et ainsi de
suite. `debut` et `fin` sont en ISO UTC.

**Champs** :
- `debut`, `fin` ;
- l'état de l'interrupteur ;
- les comptes lus ;
- par lancement : file, lot, ligne d'intention, identifiant de session ;
- par lot non lancé : son motif. Les motifs sont plafond, budget, voie
  Mac, file occupée, orphelin, arrêt, doute ou contrôle refusé ;
- par file : « carnet vide », ou le nombre de lots `bloque`. La routine ne
  les débloque pas et n'inscrit rien ([[D-510]] §4 et §5 restent aux
  sessions). Une file sans lot lançable depuis vingt-quatre heures donne
  une ligne `autre` à la boîte D ;
- l'hygiène jouée ou non ;
- les erreurs, par code ou par classe, jamais par message brut ni pile ;
- la dépense, si elle est connue.

Pas de texte libre recopié des registres. Le cockpit pourra afficher le
journal (L5) ; la base fait foi.

**§10 — Mise en service par phases.** Chaque phase attend la précédente.
Ce texte ne crée ni ne lance aucune routine.

1. **Second essai à blanc**, sans écriture au carnet ni lancement de lot.
   - **Routine.** Créée par le responsable depuis l'interface, dépôt
     sélectionné, elle joue une passe à vide. Il faut y constater :
     - le clone ;
     - `gh` authentifié et `nettoyage-branches.sh` jouable ;
     - la présence des outils de session, sans appel ;
     - les crochets actifs ;
     - la lecture de l'interrupteur et des registres ;
     - le déclenchement sur événement GitHub, si l'option retenue
       l'exige.
   - **Session de sonde.** Une seule, lancée à la main sur aucun lot. Il
     faut y constater :
     - les crochets ;
     - `gh` ;
     - la lecture des registres par l'adresse reçue ;
     - la présence de Codex ;
     - l'arrêt sur ordre.
2. **Lot de mise en service**, Mac, P1. Il verse :
   - le gabarit du premier message ;
   - les champs `lieu` et `nature` du carnet ;
   - les lignes d'intention, le document d'arrêt et le journal ;
   - la boîte `orchestrateur` dans l'énumération du code ;
   - la consigne de la passe ;
   - la mise à jour de `CLAUDE.md` et de `ROLES_MACHINES.md` pour les
     sessions lancées.

   Ses bancs :
   - double passe, double lancement ;
   - lancement sans prise qui expire ;
   - lot orphelin ou renvoyé ;
   - prise tardive passé l'échéance ;
   - lot neuf sans branche ni handoff ;
   - lot passé à `fait` sans PR ;
   - interrupteur non booléen ;
   - champ malformé ;
   - lot clinique `pret` déclaré `cloud` ;
   - lecture paginée incomplète.
3. **Pilote** (L4 du plan) : file D seule, `N` = 1, deux semaines, aux
   valeurs de `20261118-2312-d`. Ses mesures :
   - le délai entre « prête » et le lancement suivant ;
   - les lancements sans prise ;
   - les lots orphelins ;
   - les lots rangés `bloque` ;
   - les passes dégradées ;
   - la dépense.

   Le rapport va à la boîte D et en séance.
4. **Généralisation** (L6) aux autres files, à la valeur de `N` qui sera
   arbitrée. Elle attend trois choses, dans cet ordre :
   - le rapport du pilote ;
   - l'outillage durci de l'intégrateur (L3 : origine des déclarations,
     bail unique, journal des merges, délai de repentir), parce que plus
     de lots en cloud font plus de PR à merger ;
   - la parole du responsable.

Le cockpit (L5a, livré) affichera le journal et l'état de l'interrupteur
dans un lot d'affichage. Un interrupteur posé depuis le cockpit relève du
circuit de réponse de L5b, et donc d'une décision à part.

**Ce qu'elle ne décide pas.**
- Les valeurs de départ : question `20261118-2312-d`.
- La valeur de `N` à la généralisation.
- Les E2E, `test:worktree` ou l'intégrateur en cloud : l'option « tout en
  cloud » de `20261117-0113-d` n'a pas été retenue.
- L'identité séparée des sessions, qui écrivent sous le compte du
  responsable (verrou de `20261112-1703-g`, limite connue).
- Un chien de garde hors session.
- Toute reprise, par la routine, d'un geste qui revient au responsable.
