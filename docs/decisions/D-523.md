Elle ne touche pas non plus à la séparation migration / code dépendant, ni à la règle « Pas de SQL destructif sans confirmation explicite ».

## Pourquoi une autorisation bornée

Depuis [[D-520]], une migration mergée est appliquée en production sans approbation humaine : le merge est la seule porte. Jusqu'ici, la demande explicite dans la conversation restait le dernier regard humain sur une migration. La retirer pour tout ferait passer une modification de schéma, sur des données de santé hébergées en HDS, de sa conception à la production sans personne.

C'est acceptable pour ce qui se rattrape : une table, une colonne nullable ou un index en trop se retire par une migration suivante. Ce ne l'est pas pour ce qui détruit : un DROP, un TRUNCATE ou un DELETE appliqué par `release-db` ne se défait pas par un revert. Les portes qui restent sont donc mécaniques (§2) pour le réparable, et humaines (§3) pour l'irréparable.

## §1 — Autorisé sans approbation, pour toutes les sessions

1. Éditer `web/prisma/schema.prisma`. Le schéma ne touche aucune base par lui-même : ce qui l'applique est une migration, jugée au §3, ou `prisma db push`, qui reste à confirmer (§3).
2. Écrire, par Edit ou Write, une migration Prisma (`web/prisma/migrations/**/migration.sql`) ou Supabase (`supabase/migrations/*.sql`) **non destructive** :
   - CREATE (table, index, contrainte, type, fonction, trigger) ;
   - ADD COLUMN ;
   - backfill par UPDATE avec WHERE ;
   - DELETE avec WHERE.
3. Lire l'état ou l'écart des migrations : `prisma migrate status`, `prisma migrate diff` — ce dernier sans `--from-migrations` ni `--to-migrations` (qui rejouent les migrations dans une base fantôme), sans `-o|--output` (qui écrit un fichier), sans `--shadow-database-url` ni `--config` (qui peuvent désigner une autre base). Avec l'une d'elles, il demande (§3.3).
4. Migrer et jouer du SQL sur la base locale ou éphémère de son worktree, par les enveloppes qui se construisent elles-mêmes une URL locale (`scripts/wn-dev-db.sh --migrate`, `npm run test:worktree`). Une enveloppe ne dispense que lancée seule : chaînée (`&`, `&&`, `|`, `||`, `;`, retour à la ligne, substitution `$(…)`, accent grave, `<(…)`, `>(…)` — une redirection `2>&1` mise à part), la commande entière est jugée.

## §2 — Ce qui reste exigé, mécaniquement

Rien ne change sur le chemin de la production :
- l'avis Codex P0 déposé ([[D-505]]) ;
- le GO de `wn-reviewer` sur la tête ;
- la sonde `scripts/wn-sonde-release-db.mjs` à 0 ;
- une migration à la fois ;
- la sentinelle liée au run, le constat par conteneur, puis seulement le code consommateur ([[D-520]], [[D-087]]).

La règle de `db-prisma.md` sur les migrations additives (colonne nullable, drapeau éteint pour le code qui en dépend) demeure.

## §3 — Ce qui reste à la confirmation du responsable

1. Une migration **destructive**, quel que soit l'outil qui l'écrit :
   - DROP (table, colonne, index, contrainte, déclencheur…) — sauf `DROP NOT NULL`, `DROP DEFAULT` et `ON COMMIT DROP`, qui n'effacent aucune donnée ;
   - TRUNCATE — sauf `BEFORE|AFTER … TRUNCATE` d'un déclencheur et `REVOKE …, TRUNCATE`, qui ne tronquent rien ;
   - DELETE sans WHERE, UPDATE sans WHERE ;
   - renommage (RENAME) ;
   - changement de type de colonne ou d'attribut (ALTER [COLUMN|ATTRIBUTE] … TYPE), parce qu'une conversion peut tronquer des données ;
   - MERGE, qui peut supprimer ou réécrire des lignes ;
   - SQL dynamique (`EXECUTE` hors `EXECUTE FUNCTION|PROCEDURE` des déclencheurs et `GRANT|REVOKE EXECUTE ON`), qui reconstruit à l'exécution ce que le texte ne montre pas ;
   - ce qui désarme une garde de la base : `DISABLE TRIGGER|RULE`, `ENABLE REPLICA TRIGGER|RULE` (muet en mode origine), `DISABLE` ou `NO FORCE ROW LEVEL SECURITY`, `CREATE RULE`, `ALTER POLICY`, un `GRANT` à `public`, `anon` ou `authenticated` (des droits ouverts aux rôles d'API), `session_replication_role` (cherché sur le texte entier, chaînes comprises : `set_config('session_replication_role', …)`) — le journal append-only des décisions tient par ses déclencheurs.

   Le crochet d'écriture la reconnaît sur le contenu résultant (disque plus édition) et demande : autoriser vaut cette confirmation. Son principe : **ce qu'il ne lit pas avec certitude demande.**
   - Un lexeur lit le SQL comme PostgreSQL : commentaires `--` (fin de ligne `\n` ou `\r`) et `/* */` imbriqués, chaînes `'…'` et `E'…'`, identifiants `"…"`, corps `$tag$…$tag$` (étiquettes Unicode comprises). Les mots destructifs se cherchent sur le texte lexé ; un mot cité en commentaire ou en chaîne ne demande donc pas (l'en-tête « aucun DROP » des migrations reste muet).
   - Ce que le lexeur ne lit pas avec certitude demande d'office : `U&"…"`, `U&'…'`, `UESCAPE`, et toute chaîne, identifiant, commentaire ou corps non fermé.
   - Un corps `$…$` (fonction, `DO`, étiquette de toute longueur), ou une chaîne qui suit `DO [LANGUAGE x]` ou `AS` (corps entre apostrophes, décodé comme PostgreSQL le lit : `''` vaut `'`, et dans une chaîne E un `\` suivi d'un autre caractère vaut ce caractère ; un corps E qui porte `\xHH`, `\ooo` ou `\uXXXX` n'est pas lu avec certitude et demande), se lexe à son tour, récursivement : tout motif destructif, tout DELETE, tout UPDATE (sans exception de contexte : `OPEN c FOR UPDATE t SET … RETURNING` écrit), tout `EXECUTE` (sauf `EXECUTE ON`) y demande, borné ou non — le crochet ne juge pas le PL/pgSQL. Un corps qui ne se lexe pas (un littéral comme `$$Table de l'auteur$$`) se lit brut, sans aucune exception : tout mot qui écrit, détruit ou désarme y demande.
   - Un DELETE, un UPDATE (tout UPDATE qu'un SET suit dans l'instruction, hors `BEFORE|AFTER|OR|FOR|OF UPDATE` et `, UPDATE` — `UPDATE ONLY ("public"."T") * AS p SET` compris) ou un `ON CONFLICT DO UPDATE` n'est tenu pour borné que par un WHERE qui lui appartient : au niveau supérieur, après lui, et non tautologique (`true`, `1 = 1`, `not false`, parenthèses, conversions `::type` (qualifié compris) et `CAST(… AS type)`, et `AND` entre eux compris, ou l'un d'eux dans un `OR`). Placé dans une CTE ou une sous-requête, il demande : le WHERE qui suit n'est pas le sien.

   Deux passes de contre-revue l'ont façonné, le 2026-11-14 :
   - Codex : un `'--'` littéral masquait la suite d'une version qui retirait d'abord les commentaires ; puis onze formes, dont `U&"…" UESCAPE`, un `\r` seul, des commentaires imbriqués, une CTE, `EXECUTE function` (variable PL/pgSQL), une étiquette `$é$` ; puis cinq : `DO '…'`, `UPDATE ONLY (t)`, une étiquette `$…$` de plus de 128 caractères, `migrate diff --to-migrations`, `| env psql` ; puis deux : un `''--''` non décodé dans un corps entre apostrophes, `true::pg_catalog.bool` ;
   - `wn-reviewer` : un `"where"` identifiant, `$q$where$q$`, une apostrophe ou un `--` dans un identifiant, `E'\''`, MERGE, un commentaire entre ALTER et TYPE ; puis un nom qualifié, un corps `$$` contenant une apostrophe, une CTE, `ON CONFLICT DO UPDATE` ; puis les corps entre apostrophes, `set_config`, un `-- or` ou un `/**/` dans un corps lu brut, `UPDATE t * AS p`, l'enveloppe suivie d'un `&` ou d'un `<(…)`, `migrate diff -o`, `ENABLE REPLICA TRIGGER`, `ALTER ATTRIBUTE … TYPE`.

   Chacune a son cas au banc. Sur les 147 migrations du dépôt, 106 passent en silence ; les autres portent un DROP, du SQL dynamique ou une écriture dans un corps de fonction.
2. Une migration écrite **par Bash** (`cp`, redirection d'une sortie de `prisma migrate diff`, `migrate diff -o|--output`…) ou citée par un interpréteur : le SQL réellement écrit n'est pas dans la commande, il ne se juge pas, donc elle demande. La forme sans demande est d'écrire la migration par Write, où son contenu se juge.
3. `prisma migrate deploy|dev|reset|resolve`, `prisma db push`, `prisma db execute` et `prisma migrate diff` avec `--from-migrations`, `--to-migrations`, `-o|--output`, `--shadow…` ou `--config`, hors des enveloppes locales : le garde ne sait pas quelle base ils visent. Une version épinglée (`prisma@7`) ou une option avant la sous-commande (`prisma --config x migrate deploy`) ne les masquent pas. Le silence de `status` et `diff` exige une commande que le garde lit en entier : un guillemet, un `$`, un accent grave ou une barre oblique (le shell y assemble `--from-"migrations"` ou cache un `$(: migrate diff)`), ou un `db`/`migrate` avant la sous-commande, le retirent. Une sortie Prisma versée par `|` dans autre chose qu'un lecteur qui n'écrit aucun fichier (`head`, `tail`, `grep`, `more`, `cat`, `wc` — pas `sort -o`, `uniq - fichier` ni `less -o`), ou placée dans une substitution (`<(…)`, `$(…)`, accent grave) hors guillemets doubles, demande.
4. Toute écriture en production hors `release-db` (inchangé : la production se lit depuis un conteneur, et s'écrit par migration seulement, [[D-087]]).
5. L'exécution de SQL destructif en Bash reste **refusée**, comme avant : le responsable la lance lui-même s'il la confirme.

## Limites, dites sans sur-promettre

- Le crochet juge le texte, il n'exécute rien. Une destruction portée par une fonction déjà en base, appelée par la migration (`SELECT purge()`), ne se voit pas dans le texte. La contre-revue Codex et `wn-reviewer`, avant le merge, restent la porte de fond.
- Un `CREATE OR REPLACE FUNCTION` qui remplace le corps d'une fonction de garde existante (le déclencheur append-only, par exemple) par un corps vide passe en silence s'il ne contient ni DELETE ni UPDATE : le crochet ne sait pas qu'elle garde quelque chose. La revue le voit ; ce lot ne l'outille pas.
- `npx "prisma" migrate deploy` (nom cité) ou un `prisma \` suivi d'un retour à la ligne échappent au motif Prisma, et `prisma db seed` n'est pas gardé : trous antérieurs à ce lot, non aggravés, relevés par `wn-reviewer` le 2026-11-14 ; ce lot ne les ferme pas.
- `CREATE POLICY … USING (true) WITH CHECK (true)` ouvre la RLS sans DISABLE et passe en silence (`ALTER POLICY`, lui, demande) ; un WHERE comme `t.id = t.id` aussi. Relevés par `wn-reviewer` le 2026-11-14 ; la revue les voit, ce lot ne les outille pas.
- Une substitution entre guillemets doubles (`psql -c "$(npx prisma migrate diff … --script)"`) est masquée avant le jugement, comme tout texte cité : elle passe en silence, et `psql -c "$(npx prisma migrate deploy)"` aussi. Une sortie écrite dans un fichier puis passée à un client SQL (`… --script > /tmp/d.sql && psql -f /tmp/d.sql`) aussi. Trou antérieur à ce lot, non aggravé : le juger sur le texte non masqué ferait demander chaque message de commit qui cite Prisma. Relevé par `wn-reviewer` le 2026-11-14.
- Les tautologies reconnues sont les trois formes évidentes ; un `WHERE id IS NOT NULL` touche aussi toutes les lignes et passe. Le crochet borne l'accident, pas l'intention.
- Une migration déjà appliquée, réécrite par Edit, n'est pas distinguée d'une migration neuve par le crochet : c'est un fichier existant modifié dans le diff, que la revue voit. Ce lot n'ajoute aucun contrôle de cette forme.
