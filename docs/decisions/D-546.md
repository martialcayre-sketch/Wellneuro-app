# D-546 — L'outillage de merge de l'intégrateur entre au dépôt, avec ses bancs, et se durcit : origine des déclarations, délai de repentir de dix minutes, bail unique, journal des merges (amende D-454)

- Date : 2026-11-20
- Statut : accepté. Il applique la réponse du responsable à la question
  `20261113-1941-d` (2026-11-13) : « Verser et durcir, avec délai de
  repentir ». La réponse note : « Suite : lot L3 (P0, D-xxx amendant
  D-454) […]. Contestable à la prochaine séance. » Texte rédigé par
  l'assistant. Le lot est `orchestrateur-l3-integrateur` (carnet de la
  file D, D-540 §10 (4)).
- Domaine : merge des PR ordinaires (`D-373`, `D-454`) ;
  `scripts/wn-integrer.mjs` ; `scripts/wn-guetteur.mjs` (sonde `prete`) ;
  `scripts/lib/origine-declaration.mjs` ; `CLAUDE.md` § PR, CI, merge ;
  `docs/claude/REGLES_PR_MERGE.md` ; `docs/ROLES_MACHINES.md`.
- **Amende** [[D-454]] :
  - le §1 : un merge de l'intégrateur passe aussi les gardes des §2 à §4
    ci-dessous ;
  - l'amendement du 2026-11-08 : le filet passe par le même script (§6).
- **Ne touche pas** :
  - le délai de prise en charge de cinq minutes ([[D-454]] §2) ;
  - le filet de vingt minutes, ce qui fait foi et ce qui se consigne au
    journal de H89 ([[D-454]] §4) ;
  - les lots gardés par leur file (migration, authentification,
    `.coderabbit.yaml`, `pr_agent.yml`), qui ne se déclarent pas ;
  - les revues opposables ([[D-393]] §2, [[D-448]], [[D-499]]) ;
  - les étapes 7 bis et 7 ter ;
  - la protection de `main` ; l'auto-merge, qui reste coupé ;
  - [[D-540]] : une session lancée ne merge jamais.

**§1 — Versement.** Le script de merge de l'intégrateur et son guetteur
vivaient hors dépôt, sans PR, sans revue, sans banc ni historique. Ils
entrent au dépôt :

- **`scripts/wn-integrer.mjs` remplace `integrer.sh`.** Il garde ses
  étapes, leur ordre et leurs codes :
  - déploiement observé ;
  - contrôle de fusion ;
  - chevauchement ;
  - sonde release-db ;
  - `main` inchangé ;
  - tête inchangée ;
  - PR empilées ;
  - merge lié au sha revu ;
  - avance de la copie principale par `--ff-only`.

  Il y ajoute les gardes des §2 à §5. Son banc est
  `scripts/wn-integrer.test.mjs`, joué au CI par `bancs-outillage-check`.
- **La sonde `prete` de `scripts/wn-guetteur.mjs` remplace `guetter.mjs`.**
  Elle était versée depuis le 2026-11-13 (#2076), sans le contrôle
  d'origine que le guetteur hors dépôt avait reçu le même soir. Elle le
  reçoit, avec ses mots : `provenance=ok` ou `CONTROLE-INDETERMINE(…)`.

**§2 — Origine des déclarations.** L'intégrateur ne sert une déclaration
« prête @<sha> » qu'à deux conditions :

- son auteur est le propriétaire du dépôt, par le login et par
  `author_association` ;
- la tête de la PR vient du dépôt lui-même, et non d'une fourche.

Sinon, aucun merge (code 19). La fonction est unique
(`scripts/lib/origine-declaration.mjs`) et sert au guetteur comme au
script. Une origine illisible n'est jamais « ok ».

Les sessions écrivent toutes sous le compte du propriétaire : ce contrôle
écarte un tiers, il ne distingue pas une session d'une autre.

**§3 — Délai de repentir.** Aucun merge avant **dix minutes** après la
déclaration servie, c'est-à-dire le dernier commentaire « prête » qui vise
le sha à merger (code 20). **Une déclaration modifiée n'est jamais
servie** : une déclaration barrée, ou un ancien commentaire réécrit en
« prête », ne valent rien. La file redéclare par un commentaire neuf.

- **Ce qui suspend.** Toute parole sur la PR postérieure à la déclaration
  suspend le merge (code 21) :
  - un commentaire, créé ou modifié après elle ;
  - une revue soumise ;
  - un commentaire en ligne, créé ou modifié après elle.

  Le texte de la parole n'est pas lu : un refus ne se reconnaît pas par ses
  mots. Une parole de robot suspend aussi, comme le voulait déjà la règle
  « une remarque de bot arrivée après prête revient à la file ». La
  modification d'un résumé de robot après « prête » suspend donc aussi.
  Une parole datée de la même seconde que la déclaration compte.
- **Ce qui ne suspend pas.** Un commentaire de l'intégrateur : un
  commentaire de conversation, du propriétaire du dépôt (login et `OWNER`,
  comme au §2), dont la première ligne est la marque
  `<!-- wn-integrateur -->` (prise en charge, attente d'une sonde). Une
  revue, un commentaire en ligne, un robot, un tiers ou une marque citée
  plus bas suspendent toujours.
  L'intégrateur signale ainsi sa prise en charge ([[D-454]] §2) sans
  suspendre son propre merge.
- **La reprise.** Après une suspension, la file redéclare par un
  commentaire « prête @<sha> » neuf, et le délai repart de lui. Un sha
  neuf demande toujours une déclaration neuve.
- **La relecture.** La parole et la tête se relisent juste avant le merge.
  Une parole arrivée pendant le contrôle de fusion suspend donc encore.
- **Pour les files.** Après « prête », une file n'écrit plus sur la PR. Une
  précision, un verdict ou un rendu de Codex tardifs se postent, puis la
  file redéclare.

Le délai donne la possibilité de refuser, sans garantir qu'un refus
arrive : un refus dit ailleurs que sur la PR doit y être porté dans les dix
minutes. La valeur vient de la réponse `20261113-1941-d`. Elle n'a pas de
base mesurée et reste contestable en séance.

**§4 — Bail unique.** Seule la session qui tient le bail merge (code 22).

- **Où.** Le bail est un fichier du répertoire Git commun du clone
  (`<git-common-dir>/wn-integrateur/bail.json`), jamais suivi ni poussé.
  L'intégrateur n'occupe que la copie principale ([[D-373]] §2) : un clone,
  un bail.
- **Qui.** La session est identifiée par `WN_S`, son scratchpad, que
  `integrer.sh` exigeait déjà.
- **Comment.** Le bail se prend et se rend explicitement (`bail prendre`,
  `bail rendre`). Lecture, contrôle et écriture se font sous un verrou
  exclusif : de deux opérations simultanées, une seule passe, et l'autre
  est refusée sans nouvel essai. Un bail illisible n'est jamais libre.
- **La reprise.** Une autre session est refusée tant que le bail est tenu.
  Une session qui succède à un intégrateur disparu le reprend en le disant
  (`bail prendre --reprendre`). La reprise est écrite au journal, avec la
  session reprise.
- **Pas d'expiration.** Le bail n'expire pas : aucune durée n'est inventée,
  et une reprise reste un geste déclaré, jamais une expiration silencieuse.
- **Avant un `/clear`.** Le scratchpad change avec la session, donc
  l'intégrateur rend son bail avant un `/clear` ou une fin de session. La
  reprise sert à succéder à une session disparue sans l'avoir rendu.

**§5 — Journal des merges.** Chaque passage du script ajoute une ligne JSON
au journal (`<git-common-dir>/wn-integrateur/journal.jsonl`), refus
compris :

- l'heure ;
- la PR, le sha, le mode et la session ;
- le code et son motif ;
- le commit de merge, s'il y en a un.

Les prises, rendus et reprises du bail y sont aussi écrits. Le journal n'est
ni suivi ni poussé : il ne contient ni texte de PR, ni donnée patient. Il se
lit par `node scripts/wn-integrer.mjs journal`. Il ne remplace ni le
commentaire de PR, qui fait foi, ni la ligne `merge_fait` du registre
([[D-503]]), ni les fragments du journal de H89 ([[D-454]] §4).

**§6 — Le filet passe par le même script.** Une file qui merge sous le
filet de [[D-454]] (amendement du 2026-11-08) joue
`wn-integrer.mjs <N> <sha> --filet`, depuis son worktree. Ce mode :

- exige une déclaration vieille de vingt minutes au moins ;
- refuse si l'intégrateur a commenté depuis, par un commentaire marqué :
  la PR est alors prise en charge ;
- applique l'origine et la suspension par une parole ;
- ne demande pas de bail et n'avance pas la copie principale ;
- écrit au même journal.

Dans tous les modes, le script refuse (code 9) si `scripts/` diffère du
`main` vu au début du passage. Les gardes jouées sont donc celles de
`main`, jamais celles d'une branche. Le filet se joue depuis un worktree
détaché sur `origin/main`, pas depuis la branche de la PR.

**§7 — Codes de sortie.** Les codes d'`integrer.sh` sont gardés :

| Code | Sens |
| --- | --- |
| 0 | merge fait, ou contrôles verts en `--sans-merge` |
| 9 | usage, hors de la copie principale, ou `scripts/` différent de `main` |
| 11 | déploiement |
| 12 | contrôle de fusion |
| 13 | chevauchement |
| 14 | sonde release-db |
| 15 | `main` a bougé |
| 16 | tête déplacée |
| 17 | merge refusé, ou PR non ouverte |
| 18 | PR empilées |

Les codes neufs :

| Code | Sens |
| --- | --- |
| 10 | lecture GitHub impossible |
| 19 | origine non vérifiée |
| 20 | délai de repentir non échu |
| 21 | parole après la déclaration |
| 22 | bail |
| 23 | aucune déclaration « prête » sur ce sha |
| 25 | PR mergée, mais l'avance `--ff-only` de la copie principale a échoué : à arbitrer |

La garde « `main` inchangé » compare le `main` distant à celui vu au début
du passage, juste avant le merge aussi, et non à un `origin/main` relu.

`--sans-merge` joue tous les contrôles sans merger : le délai et le bail y
sont dits, sans être exigés.

**§8 — Mise en service.** Elle a lieu au merge de la PR qui porte cette
décision. Cette PR est mergée avec l'ancien outillage. L'intégrateur prend
ensuite le bail et bascule sur les scripts du dépôt, puis le dit dans sa
ligne `merge_fait`. Les fichiers hors dépôt ne sont ni modifiés ni
supprimés par ce lot.

**Ce qu'elle ne décide pas :**

- une autre valeur du délai ;
- une restriction des interactions GitHub aux collaborateurs, qui est un
  réglage du responsable ;
- la distinction d'identité entre sessions et responsable ;
- une file de merge GitHub ;
- l'extension de l'intégrateur aux lots gardés par leur file.
